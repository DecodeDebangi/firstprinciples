## Why it's easy to get wrong

Binary search fits in eight lines, yet small variations break it: `<` or `≤`, `mid` or `mid + 1`, `length(a)` or
`length(a) − 1`. Each choice looks harmless on its own. The trouble is that they have to **agree** with each other,
and guessing them one at a time is how off-by-one bugs happen.

## The fix: decide your invariant first

An **invariant** is a sentence that stays true at every step of the loop. For binary search it describes where
the answer can still be:

> *"If the target is present, it's somewhere in `a[lo..hi]`."*

Once you've written that sentence down, every other choice follows from it:

1. **Initialise** so it's true at the start: the whole array, `lo ← 0, hi ← length(a) − 1`.
2. **Loop while the range is non-empty**: for an inclusive range, that's `lo ≤ hi`.
3. **Update so it stays true**: you've checked `mid` and it isn't the target, so exclude it: `lo ← mid + 1` or `hi ← mid − 1`.

In the animations below, the Variables panel shows the current range at every step, so you can check that the
sentence stays true.

## Template 1: Closed interval, find a match

`lo` and `hi` are both still possible answers, so the range includes both ends. Writing it as `[lo, hi]`, with
square brackets, means exactly that. Use this template when you only need to know whether the target is there.

## Template 2: Half-open interval, find the first position

This template changes one thing: `hi` points one place *past* the last possible answer. The round bracket in
`[lo, hi)` means "`lo` included, `hi` not", which is why it's called **half-open**. The invariant becomes *"the
first index with `a[i] ≥ target` is somewhere in `[lo, hi)`"*.

It finds the **first** of several equal values, tells you where the target **would go** if it's missing, and needs
no special cases.

<Viz client:visible approach="lower" />

| | Closed `[lo, hi]` | Half-open `[lo, hi)` |
|---|---|---|
| Start | `lo, hi ← 0, length(a) − 1` | `lo, hi ← 0, length(a)` |
| Loop | `while lo ≤ hi` | `while lo < hi` |
| Move right | `lo ← mid + 1` | `lo ← mid + 1` |
| Move left | `hi ← mid − 1` | `hi ← mid` |
| Returns | an index of the target, or −1 | first index with `a[i] ≥ target` |
| Use for | "Is it there?" | First/last occurrence, insertion point, "first true" |

## Spot the bug

This version mixes the two templates: an inclusive `hi` with `lo < hi`, and `lo ← mid` instead of `mid + 1`. When
the range shrinks to two items, `mid` equals `lo`, so `lo ← mid` changes nothing and the loop runs forever.

<Viz client:visible approach="buggy" />

The rule that prevents it: **every iteration must shrink the range.** If an update can leave `lo` and `hi` both
unchanged, it's a bug.

## The same idea, everywhere

Many problems don't look like binary search, but are. They ask for the first position where something becomes
true: the first bad version of some software, the smallest speed that finishes on time, the first day a plant
blooms. As long as the answer is "no" up to some point and "yes" from then on, the half-open template finds that
point. Just replace `a[mid] < target` with `not condition(mid)`.

## Interview theory

<QA q="Why write mid = lo + (hi − lo) / 2 instead of (lo + hi) / 2?">
In languages with fixed-size integers (Java, C++), `lo + hi` can overflow when both are large. `lo + floor((hi − lo) / 2)`
computes the same midpoint without the overflow. Python's integers don't overflow, but the habit is worth keeping.
</QA>

<QA q="How do you find the last occurrence of a value?">
Find the first index with `a[i] > target` (the same template, with `≤` instead of `<`), then step back one. Most
standard libraries do the first half for you (see the next question).
</QA>

<QA q="What do the standard library binary searches return?">
Two answers, which together bracket every copy of `x`: the **lower bound**, the first index with `a[i] ≥ x` (the
half-open template above), and the **upper bound**, the first index with `a[i] > x`. Python calls them `bisect_left`
and `bisect_right`, C++ calls them `lower_bound` and `upper_bound`. Java's `Arrays.binarySearch` returns some index of
`x` if it's there, and otherwise `−(insertion point) − 1`.
</QA>

<QA q="Why must the update be mid + 1 in the closed template, but can be mid in the half-open one?">
In the closed template, `mid` has been checked and ruled out, so keeping it would break the invariant (and can loop
forever). In the half-open lower bound, `a[mid] ≥ target` means `mid` might be the answer, so `hi ← mid` keeps it,
while the shrinking is guaranteed because `mid < hi`.
</QA>
