## The problem

You get the root of a binary tree. The root is at row 0, column 0; a node's left child is one row down and one column left, its right child one row down and one column right. Return the values column by column, left to right. Within a column, list them top to bottom, and when two share a row and column, smaller value first.

For the tree `[5, 3, 8, 1, 4, 6, 9]` the answer is `[[1], [3], [5, 4, 6], [8], [9]]`: 4 and 6 share row 2 and column 0, so 4 comes first.

## The key question

> **Can all three ordering rules be handled at once?**

Yes: record each node as (column, row, value) and sort those triples. Sorting by several keys at once applies all three rules together; see [Sorting as a tool](/concepts/sorting-as-a-tool/).

## Approach 1: One full walk per column

Find the leftmost and rightmost columns. Then, for each column, walk the whole tree collecting its nodes, and sort them by row and value.

<Viz client:visible approach="perColumn" />

<Complexity time="O(n · w)" space="O(n)">
**Time.** Each of the `w` columns walks all `n` nodes: **O(n · w)**, which is O(n²) for a tree leaning to one side, where every node has its own column.

**Space.** The collected nodes: **O(n)**.

**What it wastes:** each walk looks at every node but keeps only one column's worth.
</Complexity>

## Approach 2: One walk, then one sort (optimal)

Walk once, recording (column, row, value) for every node. Sort the list by column, then row, then value, and cut it into groups at each new column.

<Viz client:visible approach="sortOnce" />

<Complexity time="O(n log n)" space="O(n)">
**Time.** The walk is O(n) and the sort **O(n log n)**.

**Space.** The list of triples: **O(n)**.
</Complexity>

## Comparing the approaches

Race two approaches on the same input. Both share one clock that ticks once per operation, so the one doing extra work visibly falls behind.

## Common mistakes

- **Breaking ties by order of discovery.** Two nodes in the same row and column go smallest value first.
- **Sorting by row before column.** The column decides the group; row and value only order within it.
- **Assuming columns start at 0.** Left children go negative; group by the sorted columns, not by index.
