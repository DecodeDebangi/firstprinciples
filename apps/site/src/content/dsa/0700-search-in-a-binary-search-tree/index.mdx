## The problem

You get the root of a binary search tree and a value `val`. Return the node that holds `val` (with everything below
it), or `none` if no node does.

For the tree `[8, 3, 10, 1, 6, null, 14, null, null, 4, 7, 13]` and `val = 7`, the answer is the node 7. Looking for
`5` returns `none`.

## The key question

> **At each node, does the value have to be searched for on both sides?**

No. In a [binary search tree](/concepts/binary-search-trees/), everything smaller sits on the left and everything bigger
on the right, so one comparison rules out a whole side.

## Approach 1: Check every node

Search the way you would in any binary tree: the node, then all of its left subtree, then all of its right subtree.

<Viz client:visible approach="every" />

<Complexity time="O(n)" space="O(h)">
**Time.** When the value isn't there, every one of the `n` nodes is checked: **O(n)**.

**Space.** The recursion goes as deep as the tree: **O(h)**.

**What it wastes:** it searches subtrees the order already rules out, like everything right of 10 when looking for 7.
</Complexity>

## Approach 2: Follow the order (optimal)

Start at the root. Smaller: go left. Bigger: go right. Stop when you find it or fall off the tree.

<Viz client:visible approach="follow" />

<Complexity time="O(h)" space="O(1)">
**Time.** One node per level: **O(h)**, the tree's height. That's O(log n) when the tree is balanced, and O(n) when it
has become a chain (see [Balanced trees](/concepts/balanced-trees/)).

**Space.** A single pointer, no recursion: **O(1)**.
</Complexity>

## Comparing the approaches

Race two approaches on the same input. Both share one clock that ticks once per operation, so the one doing extra work visibly falls behind.

<Compare client:visible />

| Approach | Time | Space | Idea |
|---|---|---|---|
| Check every node | O(n) | O(h) | Ignore the order |
| Follow the order | **O(h)** | **O(1)** | One comparison picks the side |

## Common mistakes

- **Searching both sides.** That's correct but throws away the whole point of a BST.
- **Returning the value instead of the node.** The answer is the node, with its subtree attached.
- **Forgetting the empty case.** Falling off the tree means the value isn't there: return `none`.
