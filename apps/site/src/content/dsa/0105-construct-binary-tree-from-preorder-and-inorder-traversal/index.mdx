## The problem

You get the pre-order and in-order traversals of a binary tree with distinct values: `preorder` and `inorder`. Rebuild the tree and return its root.

For `preorder = [6, 2, 1, 4, 3, 9, 7]` and `inorder = [1, 2, 3, 4, 6, 7, 9]` the tree is `[6, 2, 9, 1, 4, 7, null, null, null, 3]` (level by level).

## The key question

> **Which list says where the root is, and which says how to split the rest?**

Pre-order gives the roots in building order; in-order splits each range around its root. [Building a tree from its traversals](/concepts/trees-from-traversals/) explains why two lists are needed.

## Approach 1: Scan for each root

Take the next root, then scan the other list's current range to find where it splits.

<Viz client:visible approach="scan" />

<Complexity time="O(n²)" space="O(n)">
**Time.** Each scan can run across its whole range. On a tree that leans one way the ranges shrink by one each time:
n + (n − 1) + … + 1, **O(n²)**.

**Space.** The new tree and the recursion: **O(n)**.

**What it wastes:** the same list is searched again and again for values whose positions never change.
</Complexity>

## Approach 2: Look positions up in a map (optimal)

Record every value's position once, in a map. Then each root's split point is a single lookup.

<Viz client:visible approach="map" />

<Complexity time="O(n)" space="O(n)">
**Time.** Building the map is O(n), and each of the `n` nodes costs O(1): **O(n)**.

**Space.** The map, the tree and the recursion (as deep as the tree): **O(n)**.
</Complexity>

## Comparing the approaches

Race two approaches on the same input. Both share one clock that ticks once per operation, so the one doing extra work visibly falls behind.

<Compare client:visible />

| Approach | Time | Space | Idea |
|---|---|---|---|
| Scan for each root | O(n²) | O(n) | Search the range every time |
| Map of positions | **O(n)** | O(n) | One lookup per root |

## Common mistakes

- **Copying sub-lists for each call.** Pass ranges (`lo`, `hi`) and one shared position for the next root instead.
- **Off-by-one ranges.** The root itself belongs to neither subtree.
- **Building the subtrees in the wrong order.** The next root must come from the side the list reaches next.
