## The problem

You get the root of a binary tree with `n` nodes, where `node.val` is that node's coins and the coins add up to `n`. A move takes one coin from a node to a neighbour (parent or child). Return the fewest moves so every node has exactly one coin.

For the tree `[1, 0, 0, 3, null, 0, 2]` the answer is `6`.

## The key question

> **How many coins must cross each edge?**

Exactly the subtree's excess: if the nodes below an edge hold 3 more coins than they need, 3 coins must leave across that edge; if they're 2 short, 2 must come in. It never helps to send a coin across an edge and back.

## Approach 1: Count the coins below every edge

For every node except the root, count the coins and nodes in its subtree from scratch; their difference crosses the edge above it.

<Viz client:visible approach="each" />

<Complexity time="O(n²)" space="O(h)">
**Time.** Each subtree is counted once per edge above it: **O(n²)** on a chain.

**Space.** The recursion: **O(h)**.

**What it wastes:** the same subtrees are counted again for every edge above them.
</Complexity>

## Approach 2: Each node reports its excess upward (optimal)

Bottom-up, each node returns `coins + left excess + right excess − 1`. The size of each child's report is the moves across that child's edge.

<Viz client:visible approach="once" />

<Complexity time="O(n)" space="O(h)">
**Time.** One visit per node: **O(n)**.

**Space.** The recursion: **O(h)**.
</Complexity>

## Comparing the approaches

Race two approaches on the same input. Both share one clock that ticks once per operation, so the one doing extra work visibly falls behind.

## Common mistakes

- **Ignoring negative excess.** A shortfall also costs moves: add the absolute value.
- **Forgetting the coin a node keeps.** Subtract 1 for the node itself.
- **Counting the root's report as moves.** The root has no edge above it; it always reports 0.
