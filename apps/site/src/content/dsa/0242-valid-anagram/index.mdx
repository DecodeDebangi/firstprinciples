## The problem

You get two strings `s` and `t`. Return `true` if `t` is an **anagram** of `s`: the same letters, each used the
same number of times, in any order.

`"listen"` and `"silent"` are anagrams. `"rat"` and `"car"` are not.

## The key question

> **What do two anagrams have in common, whatever their order?**

Their letter counts. Sorting reveals that by lining the letters up; counting checks it directly, without
putting anything in order.

## Approach 1: Sort both, compare

If the lengths differ, they can't be anagrams. Otherwise sort both strings: anagrams become identical, so
compare them position by position.

<Viz client:visible approach="sort" />

<Complexity time="O(n log n)" space="O(n)">
**Time.** Sorting two strings of length `n` is **O(n log n)**; the comparison is O(n).

**Space.** The two sorted copies: **O(n)**.

**What it wastes:** it computes a full order, but only the counts matter.
</Complexity>

## Approach 2: Count letters (optimal)

Count each letter of `s`. Then walk `t`, subtracting one per letter. If any count goes below zero, `t` has a
letter `s` doesn't have enough of. If every count survives, they match, because the lengths are equal.

<Viz client:visible approach="count" />

<Complexity time="O(n)" space="O(k)">
**Time.** One pass over each string: **O(n)**.

**Space.** One counter per distinct letter: **O(k)**, where `k` is the alphabet size (26 for lowercase English),
so effectively O(1).
</Complexity>

## Common mistakes

- **Skipping the length check.** Without it, counting would accept `t` as a "match" when it's missing letters `s` has.
- **Checking only that the same letters appear.** `"aab"` and `"abb"` use the same letters but different counts.
- **Unicode.** For non-English text, use a hash map, not a fixed array of 26.
