## The problem

You get the root of a binary tree. Return its values in **pre-order**: each node comes **before** both of its subtrees (node, then everything on its left, then everything on its right).

For the tree `[5, 3, 8, 1, 4, null, 9, null, 2]` the answer is `[5, 3, 1, 2, 4, 8, 9]`.

## The key question

> **When exactly is a node written down?**

The moment the walk arrives at it, before going into either child. A stack can do the same: pop a node, write it, and push its children so the left one comes out next. [Tree traversals](/concepts/tree-traversals/) compares all three depth-first orders.

## Approach 1: Recursive

Visit a node by visiting its left subtree, its right subtree and the node itself, in the order this traversal needs.
The calls waiting to finish form a stack of their own.

<Viz client:visible approach="recursive" />

<Complexity time="O(n)" space="O(h)">
**Time.** Each node is visited once: **O(n)**.

**Space.** One waiting call per level of the current path: **O(h)**, which is O(n) for a chain.

**What it wastes:** nothing in time. But the call stack is hidden, and a very tall tree can overflow it; interviewers
often ask for the version without recursion.
</Complexity>

## Approach 2: Iterative, with an explicit stack

Push the root. Repeatedly pop a node, write it down, and push its right child and then its left child. The left child is on top, so the whole left subtree comes out before the right one.

<Viz client:visible approach="iterative" />

<Complexity time="O(n)" space="O(h)">
**Time.** Each node is pushed and popped once: **O(n)**.

**Space.** The stack holds about one path's worth of nodes: **O(h)**.
</Complexity>

## Comparing the approaches

Race two approaches on the same input. Both share one clock that ticks once per operation, so the one doing extra work visibly falls behind.

<Compare client:visible />

| Approach | Time | Space | Idea |
|---|---|---|---|
| Recursive | O(n) | O(h) | The language keeps the stack |
| Iterative | O(n) | O(h) | You keep the stack |

Both visit every node once, so there's no growth chart: the iterative version only makes the stack visible and safe from
running out of call depth.

## Common mistakes

- **Pushing the left child first.** Then the right subtree comes out first, which is a different order.
- **Writing the node after its children.** That's post-order.
- **Forgetting the empty tree.** With no root, return an empty list without pushing anything.
