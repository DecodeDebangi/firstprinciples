## The problem

Given n, return the numbers from 1 to n in dictionary order: compare them as text, digit by digit, so 10 comes before 2. Do it in O(n) time with O(1) extra memory.

For `n = 23`: 1, 10, 11, …, 19, 2, 20, 21, 22, 23, 3, 4, …, 9.

## The key question

> **What shape does dictionary order of numbers have?**

A trie of digits. Under 1 sit 10 to 19, under each of those 100 to 199, and so on. Dictionary order visits a node, then everything under it, then its next sibling: a pre-order walk.

## Approach 1: Write the numbers as text and sort

Turn every number into text and sort the texts.

<Viz client:visible approach="sort" />

<Complexity time="O(n log n · D)" space="O(n · D)">
**Time.** Sorting compares texts of up to D digits: **O(n log n · D)**.

**Space.** Every number as text: **O(n · D)**.

**What it wastes:** the sort. The order has a fixed shape that can simply be walked.
</Complexity>

## Approach 2: Walk the digit trie without building it (optimal)

Start at 1. After writing cur, go to its first child (cur × 10) if that's ≤ n. Otherwise move to the next sibling (cur + 1), first backing up (cur ÷ 10) while cur ends in 9 or cur + 1 would pass n.

<Viz client:visible approach="walk" />

<Complexity time="O(n)" space="O(1) extra">
**Time.** Each move is a constant amount of work spread over the n numbers written: **O(n)**.

**Space.** Only cur, besides the answer: **O(1)**.
</Complexity>

## Comparing the approaches

Race two approaches on the same input. Both share one clock that ticks once per operation, so the one doing extra work visibly falls behind.

## Common mistakes

- **Going to cur + 1 when cur ends in 9.** 19 + 1 = 20 skips back up a level; back up first, then add 1.
- **Forgetting the n limit.** cur × 10 and cur + 1 can pass n; only go where the number exists.
- **Sorting the numbers' values.** That gives 1, 2, 3, …, not dictionary order.
