## The problem

You get a list of intervals that don't overlap, sorted by start, and one new interval. Insert the new interval, merging
it with any intervals it overlaps (touching counts as overlapping), so the result is still sorted and separate.

For example, inserting `[4, 7]` into `[0, 1], [2, 3], [5, 6], [7, 8], [9, 10]` gives
`[0, 1], [2, 3], [4, 8], [9, 10]`: it swallows `[5, 6]` and `[7, 8]`.

## The key question

> **The list is already in order. Which intervals can the new one even touch?**

Only one unbroken run of them. See [Greedy in practice](/concepts/greedy-in-practice/).

## Approach 1: Add it, sort, merge everything

Append the new interval, sort by start, and run [Merge Intervals](/dsa/merge-intervals/).

<Viz client:visible approach="sortAll" />

<Complexity time="O(n log n)" space="O(n)">
**Time.** The sort is **O(n log n)**.

**Space.** The result: **O(n)**.

**What it wastes:** it re-sorts a list that was already sorted, apart from one interval.
</Complexity>

## Approach 2: One pass: before, overlapping, after (optimal)

Copy every interval that ends before the new one starts. Then, while the next interval starts no later than the new one
ends, merge it in (take the smaller start and the larger end). Add the merged interval, then copy the rest.

<Viz client:visible approach="onePass" />

<Complexity time="O(n)" space="O(n)">
**Time.** Each interval is looked at once: **O(n)**.

**Space.** The result: **O(n)**.
</Complexity>

## Common mistakes

- **Stopping the overlap run too early.** Keep merging while the next interval starts at or before the **grown** end.
- **Forgetting to add the merged interval** when nothing overlaps it: it still goes between the two runs.
- **Off-by-one on touching.** `[1, 3]` and `[3, 5]` overlap here, so "before" means ending strictly before the new
  start.
