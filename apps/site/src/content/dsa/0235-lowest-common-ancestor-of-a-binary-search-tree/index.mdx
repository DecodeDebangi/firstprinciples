## The problem

You get the root of a binary search tree and two different nodes in it, `p` and `q`. Return their **lowest common
ancestor**: the lowest node that has both in its subtree. A node counts as part of its own subtree.

For the tree `[8, 3, 10, 1, 6, null, 14, null, null, 4, 7, 13]`, `p = 4` and `q = 7`, the answer is `6`: 4 is on its
left, 7 on its right.

## The key question

> **In a BST, can you tell from a node's value alone which side p and q are on?**

Yes. Values smaller than the node are on its left and bigger ones on its right, so there's no need to search both sides
as [Lowest Common Ancestor of a Binary Tree](/dsa/lowest-common-ancestor-of-a-binary-tree/) has to.

## Approach 1: The general one-pass search

Ignore the order and use the method for any binary tree: each call reports whether it found `p` or `q` below it, and the
first node that hears from both sides is the answer.

<Viz client:visible approach="onePass" />

<Complexity time="O(n)" space="O(h)">
**Time.** It may visit every node: **O(n)**.

**Space.** The recursion along one path: **O(h)**.

**What it wastes:** it searches subtrees that the values already rule out.
</Complexity>

## Approach 2: Walk down to the split point (optimal)

While both values are smaller than the node, go left; while both are bigger, go right. The first node that isn't on the
same side of both is between them, so it's the lowest common ancestor. The [binary search
trees](/concepts/binary-search-trees/) read shows more uses of the order.

<Viz client:visible approach="split" />

<Complexity time="O(h)" space="O(1)">
**Time.** One path down: **O(h)**.

**Space.** One pointer: **O(1)**.
</Complexity>

## Comparing the approaches

Race two approaches on the same input. Both share one clock that ticks once per operation, so the one doing extra work visibly falls behind.

|---|---|---|---|
| General one-pass search | O(n) | O(h) | Works on any tree |
| Walk to the split point | **O(h)** | **O(1)** | The values pick the side |

## Common mistakes

- **Stopping only when p and q are on opposite sides.** If the node *is* `p` or `q`, it's the answer too: use `≤`.
- **Assuming p < q.** Take the smaller and bigger of the two first.
- **Searching for p and q first.** Not needed: the walk never has to find them, only compare against them.
