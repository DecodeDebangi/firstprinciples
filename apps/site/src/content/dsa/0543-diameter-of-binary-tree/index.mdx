## The problem

The **diameter** of a binary tree is the number of edges on the longest path between any two nodes. The path never
visits a node twice, and it doesn't have to pass through the root. Given the root, return the diameter.

In the example tree, the longest path is `2 → 0 → 1 → 3 → 4 → 5 → 7`: 6 edges, bending at node 3. The path through the
root is shorter.

h below is the tree's height.

## The key question

> **Every path has one highest node, where it bends. If I know how far down each side of a node can go, I know the
> longest path that bends there. Can I find that for every node without measuring the same subtrees again and
> again?**

## Approach 1: Measure both heights at every node

For each node, compute the height of its left and right subtrees (counting nodes, so a leaf has height 1). The
longest path bending there has left + right edges. Keep the best.

<Viz client:visible approach="everyNode" />

<Complexity time="O(n²)" space="O(h)">
**Time.** Measuring a node's two heights walks its whole subtree. In a balanced tree that adds up to O(n log n), but
in a chain the root walks n − 1 nodes, its child n − 2, and so on: **O(n²)**.

**Space.** The height recursion goes as deep as the tree: **O(h)**.

**What it wastes:** a node deep down is measured again by every one of its ancestors, though its height never changes.
</Complexity>

## Approach 2: Return the height, track the best

Write the height function you'd write anyway, which returns `1 + max(left, right)`. At the moment it has `left` and
`right` in hand, it also knows the longest path bending at this node: `left + right`. Compare that with a best-so-far.
One walk, every node visited once. This is "return one thing, track another" from [Tree
recursion](/concepts/tree-recursion/).

<Viz client:visible approach="once" />

<Complexity time="O(n)" space="O(h)">
**Time.** Each node is visited once, doing O(1) work: **O(n)**.

**Space.** The recursion is as deep as the tree: **O(h)**, which is O(n) for a chain and about log₂ n when balanced.

**What it wastes:** nothing. Every node has to be looked at, so O(n) is the best possible.
</Complexity>

| Return height, track best | **O(n)** | O(h) | Check left + right while computing heights |

## Common mistakes

- **Returning `left + right` from the recursion.** The parent needs a height (one side only), not a bent path.
- **Only checking the root.** The longest path can sit inside one subtree, as in the example.
- **Counting nodes instead of edges.** With heights counted in nodes, `left + right` is already the edge count.
- **Off by one for a single node.** One node has diameter 0.
