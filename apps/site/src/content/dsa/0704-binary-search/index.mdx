## The problem

You get a list of integers `nums` sorted in increasing order, with no repeats, and a number `target`. Return the
index where `target` appears, or `-1` if it isn't in the list. The problem asks for a solution faster than
checking every element.

For `nums = [3, 8, 15, 21, 27, 34, 42, 56, 63, 77]` and `target = 63`, the answer is `8`.

## The key question

> **What does one comparison tell you when the list is sorted?**

In an unsorted list, checking `nums[i]` tells you about one position. In a sorted list, it tells you about
**every** position: if `nums[i] < target`, then everything at or left of `i` is too small as well. A single
comparison can rule out a whole block of numbers.

## Approach 1: Linear scan (brute force)

Check each number from left to right. This works on any list, sorted or not. That's its weakness here: it
ignores the one property this problem gives us.

<Viz client:visible approach="linear" />

<Complexity time="O(n)" space="O(1)">
**Time.** In the worst case (the target is last or missing) it checks all `n` numbers: **O(n)**.

**Space.** One loop variable: **O(1)**.

**What it wastes:** after seeing `nums[0] = 3 < 63`, it still checks 8, 15, 21… one at a time, even though the
sorted order already says the target must be further right. Each check rules out a single number.
</Complexity>

## Approach 2: Binary search (optimal)

Keep a window `[lo, hi]` where the target could still be. Look at the **middle** element:

- Equal to the target: done.
- Smaller than the target: the target can only be to its right, so discard the left half including `mid` (`lo ← mid + 1`).
- Bigger than the target: discard the right half including `mid` (`hi ← mid - 1`).

Each comparison throws away half of what's left. Faded cells are numbers that have been ruled out.

<Viz client:visible approach="iterative" />

<Complexity time="O(log n)" space="O(1)">
**Time.** Count how many times you can halve `n` before one element is left:

`n → n/2 → n/4 → … → 1`

After `k` halvings the window holds `n / 2ᵏ` elements. It's down to 1 when `n / 2ᵏ = 1`, i.e. `2ᵏ = n`, so
`k = log₂ n`. One more check on that last element gives at most `⌊log₂ n⌋ + 1` comparisons: **O(log n)**.

To see how small that is: for 1,000,000 numbers a linear scan may need 1,000,000 checks, while binary search
needs at most **20**, since 2²⁰ ≈ 1,000,000. Doubling the input adds just *one* more check.

**Space.** Three integers (`lo`, `hi`, `mid`) whatever the size of `n`: **O(1)**.
</Complexity>

## Approach 3: Binary search, recursive

The same algorithm, written so that each halving is a new function call on the smaller window. It's easier to
read for some people, but it isn't free. Watch the **call stack** panel: every call waits there until the one
it started returns.

<Viz client:visible approach="recursive" />

<Complexity time="O(log n)" space="O(log n)">
**Time.** Exactly the same comparisons as the loop: **O(log n)**.

**Space.** Each call adds a frame to the call stack, and none of them can finish until the deepest one returns.
The depth equals the number of halvings, about `log₂ n`, so the stack takes **O(log n)** memory. The loop
version reuses three variables instead, which is why it's O(1).

O(log n) space is small (about 20 frames for a million elements), so this rarely matters in practice. It's
still a common interview follow-up: *"what's the space complexity of your recursive version?"*
</Complexity>

## Common mistakes

- **`while lo < hi` instead of `lo ≤ hi`.** When `lo = hi` there's still one candidate left. With `<`, a target sitting there is never checked.
- **`lo ← mid` or `hi ← mid`** instead of `mid ± 1`. `mid` has already been checked. Keeping it can make the window stop shrinking, which means an infinite loop.
- **Integer overflow in `(lo + hi) / 2`** in Java or C++. With very large indices `lo + hi` can overflow. Write `lo + (hi - lo) / 2`. Python's integers don't overflow, but interviewers like to ask about it.
- **Using it on unsorted data.** Binary search's correctness depends entirely on the sorted order.
