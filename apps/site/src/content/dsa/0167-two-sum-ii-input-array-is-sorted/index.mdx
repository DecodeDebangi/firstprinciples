## The problem

You get a list `numbers` sorted in increasing order and a `target`. Exactly one pair of different positions adds
up to `target`. Return their positions **1-indexed** (the first element is position 1), and use only constant
extra memory, so the hash map from Two Sum is off the table.

For `numbers = [1, 3, 4, 7, 10, 12, 15]` and `target = 25`, the answer is `[5, 7]`: `10 + 15 = 25`.

## The key question

> **What does the sorted order let one comparison rule out?**

If the smallest value left plus the largest value left is too small, the smallest value can't pair with anything:
every other partner is smaller still. That one fact turns a search over pairs into a single walk.

## Approach 1: Brute force

Try every pair, exactly as in unsorted Two Sum.

<Viz client:visible approach="brute" />

<Complexity time="O(n²)" space="O(1)">
**Time.** `n(n − 1)/2` pairs in the worst case: **O(n²)**.

**Space.** Two loop indices: **O(1)**.

**What it wastes:** it never uses the sorting.
</Complexity>

## Approach 2: Binary search for the partner

For each number, its partner must be `target − numbers[i]`, and it can only sit to the right. The list is sorted,
so binary-search for it.

<Viz client:visible approach="binary" />

<Complexity time="O(n log n)" space="O(1)">
**Time.** `n` searches, each **O(log n)**: **O(n log n)**.

**Space.** A few indices: **O(1)**.

**What it wastes:** each search starts from scratch and learns nothing from the search before it.
</Complexity>

## Approach 3: Two pointers (optimal)

Start `lo` at the smallest value and `hi` at the largest. Too small? Move `lo` right. Too big? Move `hi` left.
Each comparison rules out one number for good, and the shelf of candidates shrinks by one.

<Viz client:visible approach="pointers" />

<Complexity time="O(n)" space="O(1)">
**Time.** Every step moves `lo` or `hi` one place inward, so at most `n − 1` steps: **O(n)**.

**Space.** Two indices: **O(1)**, which is what the problem asks for.
</Complexity>

## Common mistakes

- **Returning 0-indexed positions.** This problem is 1-indexed: return `[lo + 1, hi + 1]`.
- **Using a hash map.** It works in O(n) time but uses O(n) memory, which the problem forbids.
- **`lo <= hi`.** The two positions must differ, so the loop runs while `lo < hi`.
