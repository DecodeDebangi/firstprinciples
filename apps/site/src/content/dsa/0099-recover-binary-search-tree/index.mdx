## The problem

You get the root of a binary tree that was a binary search tree until exactly two of its values were swapped. Swap them back, changing values only, not the shape.

For the tree `[6, 12, 9, 1, 4, null, 3]` the swapped values are 12 and 3: swapping them back gives the BST `[6, 3, 9, 1, 4, null, 12]`.

## The key question

> **What does a swap do to the in-order reading?**

In-order should only go up ([Binary search trees](/concepts/binary-search-trees/)). A swap creates a drop: once if the two values sit next to each other in order, twice otherwise. The drops point straight at the culprits.

## Approach 1: Sort the in-order values and compare

Read the values in order, sort a copy, and find the two positions where they differ. Swap the values at those two nodes.

<Viz client:visible approach="sort" />

<Complexity time="O(n log n)" space="O(n)">
**Time.** Sorting the values: **O(n log n)**.

**Space.** Two lists of every value: **O(n)**.

**What it wastes:** sorting. Only the two places where the order drops matter.
</Complexity>

## Approach 2: One in-order walk, spotting the drops (optimal)

Walk in order, remembering the previous node. At each drop (previous > current), record the previous node as `first` if it's the first drop, and the current node as `second`. Swap their values at the end.

<Viz client:visible approach="walk" />

<Complexity time="O(n)" space="O(h)">
**Time.** One walk: **O(n)**.

**Space.** The walk's stack: **O(h)**. ([Morris traversal](/concepts/morris-traversal/) brings it down to O(1).)
</Complexity>

## Common mistakes

- **Stopping at the first drop.** When the swapped values aren't neighbours in order, the second culprit is at the second drop.
- **Swapping nodes instead of values.** Only the values move; the shape stays.
- **Taking the wrong side of a drop.** First drop: the bigger (earlier) value. Last drop: the smaller (later) value.
