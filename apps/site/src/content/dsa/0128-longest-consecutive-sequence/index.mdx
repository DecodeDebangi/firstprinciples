## The problem

You get an unsorted list `nums`. Return the length of the longest set of values that form a run of consecutive
integers, like `1, 2, 3, 4`. Their positions in the list don't matter. The problem asks for O(n) time.

For `nums = [10, 4, 20, 1, 3, 2, 11]` the answer is `4`: the run `1, 2, 3, 4`.

## The key question

> **How do I know a number is where a run *starts*?**

`x` starts a run exactly when `x − 1` isn't in the list. Count upward only from those starts, and every number is
counted once, inside the one run it belongs to.

## Approach 1: Sort, then count runs

Sort the distinct values, then walk once: extend the run while each value is one more than the last, otherwise start over.

<Viz client:visible approach="sort" />

<Complexity time="O(n log n)" space="O(n)">
**Time.** Sorting dominates: **O(n log n)**. The scan is O(n).

**Space.** The sorted copy of distinct values: **O(n)**.

**What it wastes:** it puts everything in order, but runs only need "is x + 1 here?", which a set answers in O(1).
</Complexity>

## Approach 2: Hash set, count only from run starts (optimal)

Put every number in a set. For each number, skip it if `x − 1` is in the set. Otherwise it's a start: count `x + 1`,
`x + 2`, … while they're in the set.

<Viz client:visible approach="set" />

<Complexity time="O(n)" space="O(n)">
**Time.** Building the set is O(n). The inner `while` loop looks like it could make this O(n²), but it only runs
from run starts, and each number is stepped over by exactly one run. Across the whole loop that's at most `n`
extra steps: **O(n)**.

**Space.** The set: **O(n)**.
</Complexity>

## Common mistakes

- **Counting upward from every number.** Without the `x − 1` check, a run of length `n` is counted `n` times: O(n²).
- **Forgetting duplicates.** `[1, 2, 0, 1]` has a run of length 3, not 4. A set (or deduplicated sort) handles it.
- **Empty input.** Return 0.
