## The problem

You get the root of a binary search tree. Return the smallest difference between the values of any two different nodes.

For the tree `[40, 20, 70, 10, 30, 60, 90, null, null, 25]` the answer is 5: 20 and 25 are 5 apart, and so are 25 and 30.

## The key question

> **In a sorted list, where can the two closest values be?**

Next to each other. If a value sat between them, it would be closer to both. A BST's in-order walk is that sorted list, so each value only needs comparing with the one just before it.

## Approach 1: Compare every pair

Collect the values and compare every pair, keeping the smallest gap. It ignores that the tree is sorted.

<Viz client:visible approach="pairs" />

<Complexity time="O(n²)" space="O(n)">
**Time.** n(n − 1)/2 pairs: **O(n²)**.

**Space.** The list of values: **O(n)**.

**What it wastes:** almost every comparison. Only neighbours in sorted order can be the closest pair.
</Complexity>

## Approach 2: In-order walk, comparing neighbours (optimal)

Walk the tree in order, remembering the previous value. Each new value's gap to the previous one is a candidate.

<Viz client:visible approach="inorder" />

<Complexity time="O(n)" space="O(h)">
**Time.** Each node is visited once: **O(n)**.

**Space.** The recursion: **O(h)**.
</Complexity>

## Comparing the approaches

Race two approaches on the same input. Both share one clock that ticks once per operation, so the one doing extra work visibly falls behind.

|---|---|---|---|
| Compare every pair | O(n²) | O(n) | All pairs |

## Common mistakes

- **Comparing each node only with its children.** The closest value to a node can be far away in the tree, like a node and the smallest value of its right subtree.
- **Forgetting the previous value between calls.** It must carry across the whole walk, not reset in each call.
- **Using abs() and comparing in the wrong order.** In order, each value is bigger than the previous one, so node.val − prev is never negative.
