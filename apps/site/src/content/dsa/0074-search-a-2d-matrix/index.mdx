## The problem

You get a grid of whole numbers with `m` rows and `n` columns. Each row is sorted from left to right, and the first value
of each row is bigger than the last value of the row before it. Return whether a target value appears in the grid.

For example, the grid with rows `1 4 6 9`, `11 13 17 20` and `24 28 31 35` contains 17 but not 12.

## The key question

> **The grid has two dimensions. Is it secretly just one sorted list?**

Reading row after row never goes down, so yes. [Grids](/concepts/grids/) shows how to number the cells.

## Approach 1: Check every cell

Compare every cell with the target.

<Viz client:visible approach="scan" />

<Complexity time="O(m · n)" space="O(1)">
**Time.** **O(m · n)**.

**Space.** **O(1)**.

**What it wastes:** all of the ordering. Each comparison could rule out half the grid.
</Complexity>

## Approach 2: Binary search as one long list (optimal)

Number the cells 0 to `m · n − 1` in reading order. Cell `i` is at row `floor(i / n)`, column `i % n`. Run an ordinary
[binary search](/dsa/binary-search/) over those numbers, looking each one up in the grid.

<Viz client:visible approach="binary" />

<Complexity time="O(log(m · n))" space="O(1)">
**Time.** **O(log(m · n))**, which is the same as `O(log m + log n)`.

**Space.** **O(1)**: the list is never built, only its positions are converted.
</Complexity>

Two searches also work: binary search the first column for the right row, then binary search inside that row. Same
O(log m + log n), with a little more code.

## Common mistakes

- **Dividing by the number of rows.** Row is `floor(i / n)` where `n` is the number of **columns** (the row length).
- **Copying the grid into a list first.** It works but costs O(m · n) time and space, losing the point.
- **Using this on a grid that's only sorted along rows and columns separately.** Then reading row by row isn't sorted,
  and a different method (starting from a corner) is needed.
