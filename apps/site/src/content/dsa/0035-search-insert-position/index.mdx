## The problem

You get a sorted list `nums` of distinct integers and a `target`. Return the index of `target` if it's there.
If it isn't, return the index where it would be inserted to keep the list sorted.

For `nums = [2, 5, 9, 14, 20, 27, 33]` and `target = 16`, the answer is `4`: 16 belongs between 14 and 20.

## The key question

> **When binary search fails to find the target, where exactly does it stop?**

At the insertion point. When the loop ends, `lo` has just passed `hi`; everything left of `lo` is smaller than the
target and everything from `lo` on is bigger. So `lo` is the answer, with no extra work.

## Approach 1: Linear scan

Walk from the left and stop at the first number that's at least `target`.

<Viz client:visible approach="linear" />

<Complexity time="O(n)" space="O(1)">
**Time.** If the target is bigger than everything, all `n` numbers are checked: **O(n)**.

**Space.** One index: **O(1)**.

**What it wastes:** it ignores the sorted order, which could rule out half the list per comparison.
</Complexity>

## Approach 2: Binary search, return lo (optimal)

Run an ordinary binary search. If it finds the target, return `mid`. If the window empties, return `lo`.

<Viz client:visible approach="binary" />

<Complexity time="O(log n)" space="O(1)">
**Time.** Each comparison halves the window: at most `⌊log₂ n⌋ + 1` comparisons, **O(log n)**.

**Space.** Three indices: **O(1)**.
</Complexity>

## Common mistakes

- **Returning `hi` or `mid`.** When the target is missing, `hi` ends one to the left of the slot; `lo` is the slot.
- **Returning -1.** Unlike plain binary search, a missing target still has an answer.
- **Forgetting the end.** If the target is bigger than everything, the answer is `len(nums)`, and `lo` reaches exactly that.
