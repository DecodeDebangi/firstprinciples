## The problem

You get the root of a binary search tree and a value `val` that isn't in it yet. Insert `val` so the tree is still a
binary search tree, and return the root. Any valid tree is accepted.

For the tree `[8, 3, 10, 1, 6, null, 14, null, null, 4, 7, 13]` and `val = 5`, one answer hangs 5 as the right child of
4: 5 < 8, 5 > 3, 5 < 6 and 5 > 4.

## The key question

> **Where is the one place a new value can go without moving anything else?**

Where a search for it falls off the tree. Every comparison on the way down already agrees with the
[order rule](/concepts/binary-search-trees/), so the empty spot at the end does too.

## Approach 1: Recursive, down to the empty spot

Compare with the root and insert into the left or right subtree. When the subtree is empty, return a new node; each
call hands its subtree back so its parent can link the new node in.

<Viz client:visible approach="recursive" />

<Complexity time="O(h)" space="O(h)">
**Time.** One comparison per level: **O(h)**.

**Space.** One waiting call per level: **O(h)**.

**What it wastes:** the waiting calls. Nothing has to happen on the way back up except relinking children that didn't
change.
</Complexity>

## Approach 2: Loop, remembering the parent (optimal)

Walk down with two pointers: `node`, and `parent`, the last real node. When `node` falls off the tree, attach the new
node to `parent` on the correct side.

<Viz client:visible approach="iterative" />

<Complexity time="O(h)" space="O(1)">
**Time.** The same single path: **O(h)**.

**Space.** Two pointers: **O(1)**.
</Complexity>

## Comparing the approaches

Race two approaches on the same input. Both share one clock that ticks once per operation, so the one doing extra work visibly falls behind.

<Compare client:visible />

| Approach | Time | Space | Idea |
|---|---|---|---|
| Recursive | O(h) | O(h) | Each call returns its subtree |
| Loop | O(h) | **O(1)** | Remember the parent |

Both do the same comparisons, so there's no growth chart: the difference is memory, not time. In a balanced tree h is
about log₂ n; in a chain it's n (see [Balanced trees](/concepts/balanced-trees/)).

## Common mistakes

- **Forgetting the empty tree.** With no root, the new node is the whole tree.
- **Dropping the returned node.** In the recursive version, `root.left ← …` is what links the new node in.
- **Trying to rebalance.** Not needed: any valid BST is accepted, and the new node is always a leaf.
