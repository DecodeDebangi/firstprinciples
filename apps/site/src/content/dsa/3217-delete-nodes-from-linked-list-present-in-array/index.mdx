## The problem

You get an array of numbers `nums` and the head of a linked list. Delete every node whose value appears anywhere in
`nums`, and return the head of what's left. At least one node is guaranteed to survive.

For example, with `nums = [3, 8]` and the list `3 → 5 → 8 → 1 → 3`, the `3`s and the `8` go, leaving `5 → 1`. Note
that the head itself is deleted.

## The key question

> **How fast can I answer "is this value in nums?" for every node?**

The deleting part is the same unlinking walk as in [Remove Linked List Elements](/dsa/remove-linked-list-elements/),
with a [dummy node](/concepts/dummy-head/) in front. What changes the cost is how each node's check is done.

## Approach 1: Scan nums for every node

For each node, read through `nums` to see whether its value is there.

<Viz client:visible approach="scan" />

<Complexity time="O(n · m)" space="O(1)">
**Time.** For each of the `n` nodes, the check reads up to `m` values of `nums`: **O(n · m)**. With 100,000 of each,
that's 10 billion checks.

**Space.** Just the dummy and `curr`: **O(1)**.

**What it wastes:** it reads the same `nums` from the start again for every single node.
</Complexity>

## Approach 2: Put nums in a set first (optimal)

Put every value of `nums` into a [hash set](/concepts/how-hash-maps-work/) once. Then each node's check is a single
O(1) lookup. The walk itself is unchanged: `curr` starts on the dummy and looks at `curr.next`. If it must go, point
`curr.next` past it and stay put; otherwise move on.

<Viz client:visible approach="withSet" />

<Complexity time="O(n + m)" space="O(m)">
**Time.** Building the set is `m` adds, and the walk is `n` checks, each O(1) on average: **O(n + m)**.

**Space.** The set holds up to `m` values: **O(m)**.
</Complexity>

## Comparing the approaches

Both on the same list:

| Set first | O(n + m) | O(m) | one lookup per node |

## Common mistakes

- **Forgetting that the head can go.** Without a dummy node, deleting the first few nodes needs a separate loop.
- **Moving `curr` after a deletion.** The node that slides into `curr.next` hasn't been checked. In `3 → 8 → 1`
  with `nums = [3, 8]`, moving on would keep the `8`.
- **Converting nums to a set inside the loop.** Build it once, before the walk, or it costs O(m) per node again.
