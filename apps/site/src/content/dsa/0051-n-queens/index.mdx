## The problem

A chess queen attacks every square in its row, its column and both of its diagonals. Given `n`, find every way to
place `n` queens on an `n × n` board so that no queen attacks another. Each solution can be written as the queens'
columns, row by row (LeetCode asks for the board drawn as strings, which is a simple conversion at the end).

For `n = 4` there are two solutions: columns `1 3 0 2` and `2 0 3 1`. For `n = 2` and `n = 3` there are none.

## The key question

> **There are far too many ways to drop n queens on n² squares. What rule lets me reject most of them before
> building them, and how cheaply can I check it?**

Two queens can never share a row, so each row holds **exactly one** queen. That turns the problem into choosing a
column for each row, one row at a time, which is backtracking: place a queen in a safe column, solve the next
row, then pick the queen up and try the next safe column.

## Approach 1: Backtracking, checking every queen

To test a square, compare it with every queen already placed. Same column means `pc = c`. Same diagonal means the
row and column differ by the same amount: on a diagonal running down to the right, `row − col` doesn't change, and
on one running down to the left, `row + col` doesn't change.

<Viz client:visible approach="scan" />

<Complexity time="O(n · n!)" space="O(n) extra">
**Time.** Row 0 has n choices, row 1 at most n − 1 (one column is taken), row 2 at most n − 2, and so on, so there
are at most about n! placements; pruning by diagonals cuts far more in practice. Each square tried is checked
against up to n queens: **O(n · n!)** as a loose upper bound.

**Space.** The column list and the recursion are both n deep: **O(n)** beyond the output.

**What it wastes:** the check. Each square rescans every queen above it, though the only facts that matter are
which columns and which diagonals are taken.
</Complexity>

## Approach 2: Column and diagonal sets

Keep three sets: the columns in use, the `row − col` values in use and the `row + col` values in use. A square is
safe exactly when its column and both of its diagonal values are unused: three lookups. Placing a queen adds its
three values, and picking it up removes them, just like the column list.

<Viz client:visible approach="sets" />

<Complexity time="O(n!)" space="O(n) extra">
**Time.** The same calls as Approach 1, but every square now costs **O(1)** to check instead of up to n. Row 0 has
n choices, row 1 fewer than n − 1 safe ones (the column and both diagonals rule some out), row 2 fewer still, so the
search is usually quoted as **O(n!)**. In practice the diagonal pruning keeps it far below that: for n = 8 there are
2,057 calls, against 8! = 40,320.

**Space.** Three sets of at most n values each, the column list and the recursion: **O(n)**.

**What it wastes:** nothing in the check. The search itself is exponential, but every call puts a queen on a square
that's safe so far.
</Complexity>

## Common mistakes

- **Checking only one diagonal.** Both `row − col` and `row + col` are needed.
- **Forgetting to remove from the sets.** Picking a queen up must undo all three set entries, or later rows see
  ghosts.
- **Trying every square instead of one per row.** Then the same placement is found in many orders.
- **Mixing up which diagonal is which.** `row − col` is fixed going down to the right, `row + col` going down to
  the left.
