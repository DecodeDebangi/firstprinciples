# Contributing to firstprinciples

firstprinciples is a learning platform. Each page explains one problem from brute force to optimal, with
animations generated by running the real algorithm and a derivation of every time and space complexity. DSA
comes first; system design and other subjects come later.

## Layout
- `apps/site/`: the Astro static site (content + pages).
- `packages/ui/`: shared tokens, the step tracer, `ArrayPlayer`, `GrowthChart`. A future Next.js dashboard
  (`apps/dashboard/`) will import this package so both apps look the same.

## Adding a problem: the checklist
Create `apps/site/src/content/dsa/<4-digit LC number>-<slug>/` with three files, copying the structure of
`0001-two-sum/`:

1. **`steps.ts`**: `example` input, `fields`, `prepare` (validate/normalise user input), one `Approach` per
   solution, and `growth` (from `measureGrowth` on a worst-case input generator).
   - Each approach's `id` appears in shareable links (`?approach=<id>&step=<n>`), so never rename it once
     the page is live, or old links will open at the wrong place.
   - Each approach's `code` is Python. Every `t.step({ line })` must point at the line actually executing.
   - `message` states the *decision* in words, with the real numbers ("27 < 63, so drop the left half"), not just
     what happened.
   - Call `t.op()` once per basic operation (comparison, lookup) so the chart counts real work.
   - **Tones** follow "lift and settle": only the cell(s) being looked at *right now* should lift
     (`compare`, `active`, `found`, `miss`). Ruled-out cells use `discard` (they sink and grey). States that
     persist across steps must rest without lifting: `settled` (confirmed/matched), `visited` (already
     handled), `side-a` / `side-b` (two regions, e.g. left and right of a pivot). A `range` draws the shelf.
   - On each key comparison, set `badge: { at, text }` (e.g. `"27 < 63 →"`) to float it above that cell.
   - Pick an example that takes 6–20 steps and makes every branch run at least once.
   - **Predict mode:** on each key decision step of the optimal approach (and any other approach where it
     helps), set `ask: { q, options, answer }`. It's asked *before* that step is shown, so the question must
     use values from before the step changes anything. Capture them first, e.g.
     `const [f0, s0] = [first, second]`. The step's `message` then explains the answer.
2. **`Viz.tsx`**: copy it unchanged. It exports the single-approach player (default) and `Compare`, the
   side-by-side race.
3. **`index.mdx`**, with sections in this order:
   - `## The problem`, **in our own words**. Never paste LeetCode's statement, examples or images. Use our own example.
   - `## The key question`: the one question every approach answers faster.
   - `## Approach N: …`, brute force first, then each improvement. Each gets `<Viz client:visible approach="…" />`
     and a `<Complexity time space>` box that **derives** both bounds and ends with what the approach wastes
     (which motivates the next one).
   - `## Comparing the approaches`: one line introducing the race, `<Compare client:visible />`, a summary
     table, and `<GrowthChart client:visible series={growth} />`.
   - `## Common mistakes`, then `## Related problems`.

   Each problem's link preview image (`/og/<slug>.png`) is generated automatically from the frontmatter.

   Frontmatter:
   - `added:` is the date the page goes up. It puts the problem under "Recently added" on the home page.
   - `leetcode:` is required: `{ number, url: "https://leetcode.com/problems/<slug>/" }`. It drives the
     "Solve on LeetCode" button at the top and the "Your turn" box at the end.
   - `reel:` (optional) is the problem's Instagram reel, as the clean URL `https://www.instagram.com/reel/<id>/`.
     Strip share-tracking queries like `?srtk=` or `?igsh=`; the schema rejects them.

Before finishing: run each approach's tracer on the example plus edge cases (no answer, smallest input,
duplicates), and check every `ask` has a valid `answer` index and no duplicate options. Run `npm run build` (it type-checks first). Screenshot a mid-animation step at 1280px and 390px
wide.

Use topic tags that the home page's study roadmap (`apps/site/src/data/roadmap.ts`) recognises, e.g.
"Sliding window", "Stack", "Linked list", "Tree", "Graph", "Dynamic programming". A problem is listed under ONE topic: its
first specific tag (generic tags like "Array", "String" and "Math" count only when nothing else matches), and
other topics it practises show it as "Also used in". Put the main technique first in `topics`. If you use a new
tag, add it to a topic there.

Each roadmap topic gets its own page at `/topics/<slug>/` once a problem practises it. The page's idea, "when to
reach for it" signals and Python template live in `apps/site/src/data/topicGuides.ts`; keep the template short
enough to fit a phone (comments under about 25 characters).

Trees: use the `"tree"` input kind (LeetCode's level order with `null`), build with `treeFromLevelOrder`, and
draw with `trees: [{ root, nodes, tones, notes, pointers }]` on a step. For a recursion's call tree, set
`layout: "compact"` (columns only for leaves, parents centred), which is far narrower than the default in-order layout. If an approach changes the tree, snapshot
the nodes for every step (`nodes.map((n) => ({ ...n }))`). Linked lists use `lists`, 2D answers use `grid` (optional
`rowLabels`/`colLabels` draw headers; empty-string cells are invisible, which suits triangular tables; `dense: true`
narrows the cells, e.g. for a timeline).

The growth chart may be left out when every approach does the same amount of work (e.g. two O(n) tree walks):
say so in one sentence under the comparison table instead of drawing identical lines.

Graphs use `graphs: [{ nodes, edges, directed, tones, edgeTones, notes, pointers }]` (nodes sit on a circle unless
you pass `pos`; edge tones are keyed `"a>b"` in the edge's listed order). A 2D map or maze uses `board: { rows, tones }`
as the main view, since the race lanes only draw the main view. Heaps: `Heap` (counts every comparison) and
`heapTree` turn a heap array into a tree. Recursion trees (backtracking, call trees): record calls with `CallTree`
(`add`, `log`), then `replay` draws the whole tree faded and lights each call; nodes may have any number of `kids`.

A new data structure needs a new renderer in `packages/ui` alongside `ArrayPlayer`, with its own step type in
`trace.ts`.

## Adding a concept (theory)
Create `apps/site/src/content/concepts/<order>-<slug>/index.mdx`. Frontmatter: `title`, `topic` (must be a roadmap
topic name; add a topic to `roadmap.ts` if needed), `kind` (`Explainer`, `Comparison guide` or `Interview theory`),
`order` (reading order within the topic), `summary`, `added`. Quote a title that contains a colon.

A concept page explains the idea in our own words, uses animations where they help (a `steps.ts` + `Viz.tsx` like a
problem, e.g. the six sorts), and ends with `<QA q="…">answer</QA>` interview questions and a
`<Quiz client:visible questions={questions} />`, with the questions in a `quiz.ts` next to the page
(`export const questions: QuizQuestion[] = [{ q, options, answer, why }]`). Each `why` must make sense on its own:
the same questions feed the question bank on `/practice/`. Options are shown in a fixed shuffled order, so `answer`
can point anywhere. It appears automatically under "Read first" on its
topic page, on the roadmap card ("1 read"), at `/concepts/`, and as background reading on every problem that
practises its topic. Test any algorithm it animates against a reference, and check every quiz answer.

## Progress and practice
Readers can mark a problem solved or shaky, and practise on `/practice/`. Everything is stored in the reader's
browser (`apps/site/src/lib/progress.ts`, one localStorage key); there are no accounts, and a backup file or code
moves it between devices. The practice bank (`lib/bank.ts`) is built from every concept's `quiz.ts`, plus a
"which technique?" and (unless the answer is O(n)) a "best complexity?" question per problem, using the first
paragraph of `## The problem` and the blockquote under `## The key question`. Keep both sections self-contained.
Question ids are stable (`p:<slug>`, `t:<slug>`, `c:<concept>:<question text>`), so renaming a slug or rewording a
quiz question resets readers' history for it.

## RSS feed
`/rss.xml` lists every problem and read, newest first, dated by `added` (`apps/site/src/lib/feed.ts`, shared with the
`/feed/` page that explains how to subscribe). Nothing to do per page: new content appears on the next build.

## Studio (reel recording)
`/studio/<slug>/` shows one problem's animation in a 9:16 frame (432 × 768 CSS px) with large text, for screen
recording. It reads the same `steps.ts`, so nothing extra is needed per problem. It isn't linked anywhere and is
kept out of search and the sitemap. `?approach=<id>` opens a specific approach.

## Look and feel
Light only, warm: cream paper, brown ink, terracotta accent; Fraunces headings, Inter body, JetBrains Mono code.
All colours are tokens in `packages/ui/src/tokens.css`. The chart series (terracotta, teal, plum) were validated
as a colour-blind-safe set; re-validate them if you change them.

## Commands
- `npm run dev`: local dev server
- `npm run build`: type-check + static build into `apps/site/dist/`
- TypeScript is pinned to 6 because `astro check` doesn't support 7 yet.
